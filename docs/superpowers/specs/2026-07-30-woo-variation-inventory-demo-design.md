## Problem Statement

The inventory dashboard must compare Zoho, the authoritative inventory source, with every sellable SKU on Shopify UAE, Shopify KSA, Shopify WA, and WooCommerce. It must make quantity mismatches, missing listings, incomplete feeds, and recent inventory changes obvious enough for Omnia to trust during a demo.

The current WooCommerce snapshot cannot support that claim. LitCommerce reports roughly 2,200 active listings, while Supabase contains 1,083 Woo SKUs. Of those database rows, 888 have a null quantity. The current Woo client fetches parent products but does not enumerate variable-product variations, where many sellable SKUs and stock quantities live.

## Demand Evidence

- Omnia needs a demo that proves the platform can identify cross-store mismatches and react when inventory changes.
- The user explicitly requires checking each Zoho SKU against every store.
- The user rejected presenting the current Woo count as complete because LitCommerce shows approximately 2,200 active product SKUs.

## Status Quo

- Zoho is the agreed inventory authority.
- Shopify and WooCommerce inventory snapshots are stored in `store_inventory`.
- The panel already contains store pulse, activity, drift, live-event, SKU-drawer, and warehouse-matrix components.
- `InventoryPanel` renders `LiveEventsTicker` twice and places the operational story in an unclear order.
- Woo parent products with `manage_stock=false` produce null quantities even when their variations are individually stock-managed.
- Webhook and reconciliation code exists, but the first delivery must establish trustworthy catalog coverage before claiming instant production behavior.

## Target User & Narrowest Wedge

The immediate user is the Omnia stakeholder evaluating whether the platform can be trusted as a cross-channel inventory control surface. The narrowest acceptable wedge is:

1. Import every sellable Woo SKU, including variations.
2. Compare each normalized Zoho SKU with all configured stores.
3. Distinguish missing listing, unknown quantity, unmanaged stock, and genuine quantity mismatch.
4. Present the evidence cleanly in the inventory panel without duplicate or misleading status elements.

## Constraints

- Zoho remains authoritative; store quantities are observations until a separately authorized push action occurs.
- Existing user changes in the dirty worktree must be preserved.
- Parent products and variations must not be double-counted.
- Products without SKUs cannot participate in SKU reconciliation and must be reported separately.
- Duplicate normalized SKUs must block automatic correction.
- Null quantity must never be silently converted to zero.
- The demo must label feed coverage and freshness truthfully.
- This delivery is configuration-driven but is accepted against the four currently configured channels: UAE, KSA, WA, and WOO.

## Data Semantics

### Sellable Woo item

- A simple product is sellable when its status is `publish`, it has a non-empty SKU, and it is not an external/grouped container.
- A variation is active for inventory reconciliation when its parent and variation statuses are `publish` and it has a non-empty SKU. `purchasable=false` does not exclude it because Woo may use that state for a published, temporarily out-of-stock listing.
- A variable parent is always treated as a container and excluded from sellable-SKU counts, even if it has an SKU. Its SKU is retained in the parent-container audit category.
- Draft, pending, private, trash, disabled, external, and grouped items are counted in audit categories but excluded from active reconciliation.
- Blank/invalid SKU audit counts include otherwise-active simple products and variations that fail SKU validation; these records cannot enter the normalized reconciliation union.

### SKU identity

- Persist the raw source SKU unchanged for audit.
- Derive `normalized_sku` by Unicode normalization, trimming surrounding whitespace, and applying the repository's existing case-normalization rule. Do not remove internal punctuation or spaces unless the existing cross-channel normalizer already does so.
- Duplicate detection is scoped within each channel after normalization. The same normalized SKU appearing once in each different store is expected; two active Woo sellable items resolving to the same normalized SKU is ambiguous and blocks automatic correction for that channel.
- Database uniqueness is enforced on source identity (`channel + product_id + variation_id`, with a stable sentinel for simple products). Normalized-SKU uniqueness is not a database constraint; ambiguity is detected after ingestion so conflicting source rows remain available for diagnostics.

### Independent state dimensions

Each SKU/channel cell has three independent dimensions instead of one overloaded status:

- Identity: present, missing, duplicate, or invalid SKU.
- Quantity: numeric, unknown, or unmanaged.
- Comparison: matched, mismatched, or not comparable.

Only `identity=present` plus `quantity=numeric` can produce matched or mismatched comparison states. Null never means zero.

### Bidirectional reconciliation

The comparison universe is the union of normalized Zoho and store SKUs. It reports both Zoho-originating SKUs missing from stores and store-only/orphan SKUs absent from Zoho.

### Snapshot safety

- Every snapshot receives a run ID and records observed rows without deactivating prior data.
- Only a run that finishes every required parent and variation page without error may become the channel's authoritative completed snapshot.
- After successful completion, rows not observed in that run are soft-deactivated; they are never hard-deleted by the sync.
- Any timeout, retry exhaustion, malformed page, or pagination-loop detection marks the run degraded/failed, preserves the previous authoritative rows, and forbids the stale-row sweep.
- Persist raw audit counts and errors on the sync run so the UI can explain degraded state.

### Feed health

- Healthy: last authoritative snapshot completed within 15 minutes, no pagination errors, zero duplicate active normalized SKUs, and observed active unique SKU count is at least 95% of the last accepted external baseline.
- Degraded: snapshot is 15–60 minutes old, unknown or unmanaged quantities exceed 5% of all observed active unique valid SKUs, duplicates exist, or coverage is below 95% of baseline.
- Stale/failed: no authoritative snapshot, last success is older than 60 minutes, or the latest attempted run failed.
- Severity precedence is stale/failed over degraded over healthy; the UI displays the highest-severity condition and lists every contributing reason.
- Until a LitCommerce export is categorized and accepted, the previous successful Woo snapshot is displayed as context only and cannot by itself produce a healthy state. The first accepted baseline comes from a Woo/LitCommerce category audit, not the approximate number hard-coded in application logic.
- Persist each accepted baseline as an immutable version containing channel, count, category definition, source artifact reference, accepted timestamp, and accepting operator. A newer accepted version supersedes but does not overwrite the previous version; health uses the latest accepted version.

## Premises

1. Reconciliation operates on normalized sellable SKUs, not top-level Woo product counts.
2. A Woo variable product requires fetching its variations from `/products/{product_id}/variations`.
3. LitCommerce's approximately 2,200 listings is a useful reconciliation target, but the exact expected total must be derived from active Woo items with non-empty unique SKUs.
4. A quantity is comparable only when Woo manages stock for the sellable item and returns a numeric quantity.
5. Webhook speed cannot compensate for an incomplete baseline snapshot.

## Approaches Considered

### Approach A: Variation-complete ingestion and truthful panel cleanup

Extend the existing Woo integration to fetch variations for variable products, persist variation identity, classify quantity states, expose coverage diagnostics, and clean the current panel hierarchy. This reuses the existing APIs and UI components and is the selected approach.

### Approach B: Full event-driven inventory control plane

Replace snapshot-oriented reconciliation with a durable event ledger, idempotent consumers, alert delivery, retry queues, and policy-controlled automatic correction. This is the long-term architecture, but it is too broad before catalog coverage is trustworthy.

### Approach C: Presentation-only facade

Shape current rows into an impressive demo without fixing Woo coverage. Rejected because Omnia can compare the displayed count with LitCommerce and immediately lose trust.

## Recommended Approach

Implement Approach A in two bounded slices.

### Slice 1: Woo variation-complete ingestion

- Extend Woo product typing to include product `type`.
- Fetch all parent products with pagination.
- For each variable product, fetch every variation with pagination through the existing Woo limiter, with at most two concurrent requests and three retry attempts for 429/5xx/network errors using exponential backoff. Snapshot timeout is configurable, defaults to 15 minutes, and is capped at 30 minutes. Before rollout, log the observed product/variation page count and duration; a timeout remains a safe failed run that cannot promote or sweep stale rows.
- Convert simple products and variations into one common sellable-item shape containing SKU, parent product ID, optional variation ID, status, stock-management state, and quantity.
- Persist raw SKUs and derive normalized SKUs before comparison.
- Detect blank and duplicate normalized SKUs and publish diagnostics instead of choosing a winner.
- Preserve null quantity as `unknown` or `not managed`; never coerce it to zero.
- Add or migrate variation-aware persistence so database uniqueness uses channel, product ID, and optional variation ID. Detect normalized-SKU duplicates after ingestion and preserve every conflicting source row for diagnostics.
- Backfill current Woo rows through the new full snapshot rather than guessing missing variation identity from legacy rows.
- Add run ID/observed-at fields or an equivalent staging mechanism to support an atomic authoritative-snapshot promotion.
- Upsert `woo_product_map` and `store_inventory` with raw SKU, normalized SKU, product/variation identity, lifecycle status, quantity state, and snapshot run ID.
- Soft-deactivate stale Woo rows only after authoritative snapshot promotion.

### Slice 2: Demo panel cleanup

- Render in this order: authoritative-source/sync strip; store pulse and coverage cards; KPI/health summary; quantity drift actions; activity chart and single live ticker; searchable comparison table; SKU drawer.
- Remove the duplicate `LiveEventsTicker`.
- Keep one store pulse row and one activity/ticker grid.
- Show Woo coverage fields: active unique SKUs, numeric quantities, unmanaged quantities, unknown quantities, blank SKUs, duplicates, last authoritative snapshot time, and accepted-baseline percentage.
- Keep drift actions separate from coverage anomalies.
- Clicking a comparison or drift row opens the audit drawer for the normalized SKU; the drawer shows raw source SKUs, identity/quantity/comparison state per channel, snapshot timestamp, and recent events. Push remains disabled when any target identity is missing/duplicate or quantity is not comparable.
- Display a degraded-state banner when coverage is incomplete or stale.
- Do not label Woo healthy until a completed snapshot and coverage checks pass.

## Open Questions

- The exact LitCommerce export definition may include drafts, parents, variations, or products without SKUs. The implementation default is the sellable definition above; validation will reconcile category counts rather than hard-code 2,200.
- Automatic cross-store pushes and external notifications remain a later, separately reviewed phase.

## Success Criteria

1. A completed Woo sync enumerates all pages of products and all pages of variations.
2. The sync reports totals for parents, parent-container SKUs, simple sellable items, variations, disabled/non-sellable variations, active unique SKUs, otherwise-active blank/invalid SKUs, duplicate SKUs, managed quantities, unmanaged quantities, and unknown quantities.
3. The active unique Woo SKU count can be explained against LitCommerce with category-level differences.
4. Every SKU in the union of Zoho and configured-store SKUs has explicit identity, quantity, and comparison dimensions for UAE, KSA, WA, and WOO.
5. Null Woo quantities are not classified as zero stock or ordinary mismatches.
6. The inventory panel contains only one live-event ticker and clearly separates catalog coverage from quantity drift.
7. The panel shows source freshness and degraded states without claiming webhook health that has not been observed.
8. Unit tests cover simple products, variable products, multi-page variations, blank SKUs, duplicate SKUs, unmanaged stock, and stale-row handling.
9. Existing inventory comparison tests and the production build pass.
10. Tests prove that a failed or partial snapshot cannot deactivate rows from the last authoritative snapshot.
11. Tests cover 429/5xx retry exhaustion, pagination-loop detection, snapshot timeout, reverse/store-only reconciliation, and health threshold boundaries.

## Dependencies

- Valid WooCommerce REST credentials with permission to read products and variations.
- Existing `woo_product_map`, `store_inventory`, and sync-run persistence.
- A LitCommerce or Woo export used only as an external count reconciliation reference.
- Schema migration authority for variation-aware identity and authoritative snapshot markers. If existing columns can represent these semantics safely, implementation may avoid a migration but must prove the constraints with tests.

## The Assignment

After deployment to the configured Omnia environment, the implementation owner runs one credentialed full Woo snapshot and saves its category audit as a dated JSON/CSV artifact outside source control. The Omnia operator compares it with a categorized LitCommerce export. If LitCommerce is unavailable, Woo REST totals and an admin product export become the fallback evidence. Woo remains degraded until the discrepancy is explained and an accepted baseline is recorded.
